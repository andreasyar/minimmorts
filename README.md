# MiniMMORTS

Браузерный HTML/JavaScript-клиент и игровой Java/WebSocket-сервер.
Для игры предназначен [релизный дистрибутив](release/README.md): готовые JAR
и статический клиент. Пользователь создаёт Docker-образы без компиляции,
Maven и Node.js. Спрайты в дистрибутив не входят;
для полноценной графики нужно подключить собственные PNG.

Общая версия клиента и сервера — **2.1.0**.

Для разработки на хосте нужны только Docker Engine и Docker Compose.
JDK 21, Maven и Node.js находятся внутри dev-контейнеров.

## Запуск для разработки

```sh
docker compose up -d --build
docker compose logs -f
```

Открыть <http://localhost:5173>. Поле Server заполняется автоматически:
`ws://localhost:5173/ws/`. Указать логин и пароль из латинских букв/цифр и подключиться.
Это адреса для браузера на той же машине, где запущен Docker.
Оба порта опубликованы только на `127.0.0.1`.

`client` запускает `npm ci` и Vite. При сохранении HTML/JS страница
перезагружается целиком: клиент пока использует обычные скрипты и общие глобальные
переменные, поэтому замены модулей с сохранением игрового состояния нет.

`server` при запуске и изменениях `server/src/`, `server/pom.xml` или
`server/config.xml` выполняет чистую сборку Maven и запускает готовый JAR.
Проверка изменений происходит раз в секунду. Успешная пересборка перезапускает JVM,
сбрасывает игру в памяти и разрывает соединения. Для повторного входа обновить
страницу клиента. При ошибке компиляции предыдущий процесс продолжает работать;
после исправления и сохранения файла сборка повторяется. Если JVM аварийно
завершилась без изменения исходников, выполнить `docker compose restart server`.

Репозиторий смонтирован в оба контейнера: редактировать файлы можно на хосте
или из контейнера. Результаты сборки и кэши находятся в отдельных Docker volumes.
SELinux bind mount использует общую метку `z` для двух сервисов.

## Команды внутри контейнеров

```sh
# Проверка и сборка сервера (/build/server/target/minimmorts-server.jar со всеми зависимостями)
docker compose exec server mvn -B -ntp clean verify

# Проверка синтаксиса и сборка клиента (dist/)
docker compose exec client npm run build

# Сквозная проверка HTTP и входа в игру (после запуска обоих сервисов)
docker compose exec -T client node /workspace/dev/smoke.mjs

# Терминалы
docker compose exec server bash
docker compose exec client sh

# Перезапуск и остановка
docker compose restart server
docker compose down
```

Ручная сборка сервера сама по себе не заменяет запущенную JVM; автоматический
перезапуск происходит при изменении исходников или через `compose restart`.
Не запускайте две Maven-сборки одновременно: дождитесь завершения автоматической
сборки в логах. Работающий сервер использует отдельную копию JAR и не зависит от
очистки каталога сборки. В контейнере Maven через `MAVEN_ARGS` использует
`/build/server/target`; вне контейнера каталог по умолчанию — `server/target/`.

Примеры извлечения результатов на хост:

```sh
docker compose cp server:/build/server/target/minimmorts-server.jar /tmp/minimmorts-server.jar
docker compose cp client:/workspace/client/dist /tmp/minimmorts-client
```

Сервер можно запускать из любого каталога:
`java -jar minimmorts-server.jar /absolute/path/config.xml`.
Без аргумента он читает `config.xml` в текущем каталоге; там же создаёт логи.
В dev-стенде логи-файлы и рабочий JAR находятся в volume `/run/minimmorts`;
консольный вывод доступен через `docker compose logs server`.

Сборка клиента сохраняет классические скрипты, порядок их загрузки и структуру
ресурсов; компиляция JavaScript в модули пока не нужна. `dist/index.html` —
основная страница для обычного статического HTTP-сервера.
Бот в `client/bot/` пока не включён в dev-стенд и сборку основного клиента.

## Зависимости и обновления

Версии инструментов заданы в `dev/*/Dockerfile`, зависимости Java — в
`server/pom.xml`, зависимости клиента — в `client/package-lock.json`.
Для сервера выбран Maven: wrapper на хосте не требуется, команда `mvn`
предоставляется образом. Изменения Dockerfile требуют `docker compose up -d --build`.
После изменения package.json нужно обновить lock-файл, затем перезапустить клиент:

```sh
docker compose run --rm --no-deps --user "$(id -u):$(id -g)" -e npm_config_cache=/tmp/npm-cache client npm run lock
docker compose restart client
```

Пример обновления lock-файла рассчитан на Linux/macOS и использует UID/GID
пользователя хоста, чтобы не создавать в репозитории файлы от root.

Netty оставлен на совместимой ветке 3.10.6.Final: исходники используют её API.
Это устаревшая ветка; перенос на поддерживаемый сетевой стек — отдельная задача,
а текущий стенд предназначен для локальной разработки.
MySQL не запускается: текущий игровой сервер не вызывает `DBWorker`.
Этот класс переведён на стандартные интерфейсы JDBC; если понадобится БД,
потребуются JDBC-драйвер, схема и сервис БД.

## Локальные ресурсы

`client/src/sprites/` исключён из Git и после клонирования отсутствует.
Для полноценного отображения нужны локальные PNG; сборка переносит их, если они
есть. Оригинальный `peasant_follow.png` отсутствует и в сохранённых архивах;
для него создан новый прозрачный маркер цели следования. Его можно воспроизвести
командой `python3 client/tools/create-follow-sprite.py` (нужна библиотека Pillow).
Эти ограничения и происхождение файлов описаны в [doc/README.md](doc/README.md).
Без ресурсов веб-сервер и игровой сервер запускаются, но графика будет неполной.

`docker compose down` сохраняет кэши и результаты. `docker compose down -v`
удаляет volumes этого стенда, включая кэши, результаты сборки и файловые логи.

## Подготовка релиза

Сборщику нужны Docker с Compose, Python 3.11+ и интернет для получения базовых
образов и зависимостей. На машине игрока нужны только Docker с Compose.

```sh
python3 release/build.py
```

Команда проверяет согласованность версий в package.json, lock-файле, Maven и
релизном Compose, собирает и проверяет клиент и сервер в многоэтапном Dockerfile,
а затем упаковывает готовые файлы, конфигурацию, Dockerfile и Compose в
`release/dist/minimmorts-2.1.0.tar.gz`. Docker-образы в архив не входят.
Пользователь выполняет `docker compose up -d --build`: Docker скачивает JRE/Nginx
и копирует готовые файлы проекта в локальные образы без инструментов разработки
и компиляции. Повторная упаковка существующего
архива запрещена; для пересборки сначала перенести или удалить старый архив.
Каталоги локальных спрайтов исключены из Docker build context; релизная сборка
также проверяет отсутствие `dist/sprites`. Исходники и локальные архивные материалы
в дистрибутив не копируются.

JAR и статические файлы не привязаны к архитектуре процессора; архив общий
для amd64 и arm64. Базовые образы при установке выбирает Docker. Запуск на каждой
заявленной архитектуре нужно проверить перед публикацией.

Распаковать результат в отдельный каталог и выполнить команды из его README.
Для сквозной проверки запущенного релиза из корня репозитория:

```sh
docker run --rm --network minimmorts-release_default \
  -v "$PWD/release/smoke.mjs:/smoke.mjs:ro,z" \
  node:24.11.0-bookworm-slim node /smoke.mjs
```

Проверка использует отдельный контейнер Node: запрашивает страницу и скрипты,
проверяет отсутствие спрайтов и вход двух клиентов через Nginx. Она не проверяет
визуальное отображение игры с пользовательским набором ресурсов.

Перед выпуском обновить общую версию в `client/package.json`, двух полях
`client/package-lock.json`, `server/pom.xml`, `release/compose.yaml` и документации;
завершить запись changelog. После проверки дистрибутива поставить тег `v2.1.0`
на проверенный коммит и приложить архив бинарников к GitHub Release. Сам по себе
автоматический архив исходников GitHub не содержит готовых файлов проекта.
